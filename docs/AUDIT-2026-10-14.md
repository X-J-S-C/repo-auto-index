## 1. 核心发现：一句假的断言

### 现象

`tools/sync.ps1` 的职责是「保证宿主运行位置与源码一致」，通过时打印：

> 校验通过：宿主运行位置与源码逐字节一致。

改完结构（App 移到 `repo-auto-index/` 子目录）后，它一直报通过。我据此认为「没问题」。

### 受控实验

**实验一**：把 `repo-auto-index/assets/icon.png` 的一个字节取反，跑 `sync.ps1 -Check`。

```
校验通过：宿主运行位置与源码逐字节一致。
EXIT=0
```

报通过。但安装目录的图标并没有变。

**实验二**：向 `repo-auto-index/sdk/app-contract/server-client.js` **追加一行**，再跑。

```
校验通过：宿主运行位置与源码逐字节一致。
EXIT=0
```

同样报通过。

**实验三（反向）**：在安装目录凭空放一个源码侧没有的文件。

```
（无任何提示）
校验通过：宿主运行位置与源码逐字节一致。
EXIT=0
```

依然报通过。

> 措辞上的自我修正：实验二是「追加一行」而不是「改一个字节」。
> 两者都能证伪断言，但记录必须与操作一致，否则下次复现会对不上。

### 根因

托管集只有 `index.js` + `manifest.json` + `ui/`。`assets/` 与 `sdk/` 不在其中，所以：

- 源码侧 `assets/`、`sdk/` 的改动**从未被比较**（实验一、二）
- 安装目录里的多余文件**从未被枚举**（实验三）

而脚本的措辞是无条件的「逐字节一致」——**它没有说"在我检查的 16 个文件上一致"，
它说了一个比实际主张更宽的命题**。这不是「覆盖不全」，是一句**假的断言**。

更准确的归类（经独立复核修正）：

> 同步域存在**第二套人工维护的描述**，没有直接锚定权威包边界。

两次失效属同一家族，但直接原因不同：

- 2026-10-13：**成员枚举漂移**。新增 `report.*` 后，六文件白名单未更新。
- 2026-10-14：**边界建模错误**。规则已按目录派生，但错误地把 App 包建模为
  `index.js + manifest.json + ui/`，从定义上就排除了既有的 `assets/` 与 `sdk/`。

所以「同一份事实存在两处」这个说法，更贴切地描述的是 `tests/assets/`（见 §3），
而不是这两次同步器失效。

### 为什么这是最危险的一类缺陷

一个漏检的检查器，输出的是**置信度**，不是信息。看到绿灯的人不会再去看别处。
2026-10-13 那次「有时新有时旧」就是这么长出来的：白名单漏了 `report.*`，
同步器报通过，于是宿主服务的是一个不存在于源码的旧版。
这次漏的是 `assets/` 与 `sdk/`——`icon.png` 与 vendored SDK。

### 修法（四条，都可复现验证）

**① 托管集改成 App 根下全部文件**，无白名单、无例外：

```
受服务文件 = App 根下全部文件（index.js / manifest.json / assets/ / sdk/ / ui/）
```

不再挑目录，也就不再有「新目录没被收进来」这个失败模式。

**② 反向核对**：枚举安装目录，报出源码侧没有的文件。不自动删（可能是宿主自己写的），
但必须报。否则「两处一致」这句话仍是假的。

**③ `*.md` 不再静默过滤**：改为在源码侧报警 + 报为漂移。
静默过滤是一种安静的谎——文件明明在 App 根下，检查器假装它不在。

**④ 多余文件改为非零退出**（经独立复核后追加）：
同步是单向的（只拷源码→安装），删过的文件不会从安装目录消失。
于是宿主静态树里可能留着源码已不存在的旧文件，而 `-Check` 报 exit 0——
**那仍是机器可见的假绿灯**：CI / 交付脚本只看退出码就会放行。
现在「一致」的完整含义是双向的：源码有的一定在、安装多的必须被看见（exit 2）。
仍不自动删——安装目录里也可能有宿主自己写的文件。非零退出的语义是
「此处有人需要看一眼」，不是「脚本自己处理」。

同时修掉一处报错路径：安装目录缺文件时 `$tHash.Substring(0,12)` 会抛异常
（空串取子串），已改为打印 `(缺失)`。

### 修复后复验（同一组实验重跑）

| 实验 | 修复前 | 修复后 |
|---|---|---|
| 改 `assets/icon.png` 1 字节 | exit 0（假通过） | **exit 2**，`[漂移] assets\icon.png 源码=2BA4EA5127C5 安装=6AF726D6B772` |
| 改 `sdk/` 下 1 行 | exit 0（假通过） | **exit 2**，`[漂移] sdk\app-contract\server-client.js` |
| 安装目录多 1 个文件 | exit 0（无提示） | **exit 2** + `[多出] _stale-old-file.txt` |
| App 根下放 `.md` | exit 0（静默忽略） | **exit 2** + `[提醒] 应放 docs/` |
| 干净态 | exit 0 | **exit 0**，`源码侧 374 个受服务文件逐字节一致，且安装目录无多余文件` |
| 新建受服务文件后跑同步 | — | **真被搬过去**，`[已同步] assets\_sync-test.txt`，复验一致 |

托管集从 16 个文件扩到 **374 个**，覆盖 App 根全部内容。

### 安全依据（为什么敢覆盖 `assets/` 与 `sdk/`）

`manifest.icon` 指向 `assets/icon.png`，SDK 文档提到宿主安装时会「生成显示副本」。
若宿主真的重新生成图标，覆盖它可能被解读为「污染宿主产物」。

实测反驳：本机安装目录 374 个文件与源码**逐文件哈希相等**（含 `icon.png` 41090 B，
字节完全相同；`sdk/` 357 文件零差异）。即**本机宿主的安装是整目录镜像复制，不做转码**。
所以覆盖不构成污染。

**这个结论绑定宿主版本，不是普适事实。** 它是「当前宿主实现的现象」，不是「平台契约」。
若日后宿主改成安装时生成派生副本，`assets/` 这一处需复核。

**可证伪的复核方法**（独立复核提出的最强反对意见，记为待办）：

1. 建一个最小 local App，在 App 根放一个**未被任何入口引用**的哨兵文件；
2. 全新安装后，在安装完成 / reload 后 / 首次运行后三个阶段各做一次双向文件清单 + 哈希比较；
3. 若出现「源文件被合法省略」「源文件被合法转换」「宿主按契约向安装目录写入新文件」
   任一种，则「全根镜像边界」需加入平台契约例外。

在出现这种证据前，以 `source.path` 对应的整个 App 根作为部署镜像边界，
风险低于自行推导运行时最小闭包。

### 2.3 本机现有 374 文件里，回归真正需要哪些

用 `tests/_assets-closure.mjs` 从 manifest 的 `cards[].route` 出发求引用闭包，结果是 **11 个**：

```
panel.html  report.html
assets/panel.js  assets/panel.css  assets/report.js  assets/report.css
assets/app-ui.js  assets/app-ui.css  assets/graph-map.js  assets/sdk.js
assets/assets/rice-paper-6AU64DSD.png
```

两处值得记录：

- `graph-map.js` 只能靠**动态 import** 发现（`panel.js:1086` 的 `await import("./graph-map.js")`）。
  宿主静态校验器那条 `DYNAMIC_DEPENDENCIES_NOT_PROVEN` warning 指的就是这类依赖。
  首版闭包脚本漏了它，是写完跟人工比对时发现的。
- `assets/sdk.js` 在闭包内，但它是**测试专属 mock**（4379 B vs 真 SDK 161706 B）。
  即：闭包告诉你“页面需要这个路径”，**覆盖它的是哪份文件由测试策略决定**。
  这两件事得分开，不能混在一个规则里。
